# Colyglot Game/3D Redesign — Design Spec

**Date:** 2026-09-26 (rev. 3 — CC0 asset pipeline + camera/layout polish)
**Status:** Draft, pending user review
**Supersedes/extends:** `DESIGN.md` (this spec does not replace DESIGN.md — it extends its Paper & Ink system into a 3D game shell; DESIGN.md's tokens, typography, and DOM component rules remain the source of truth for anything not called out here)

**Rev. 2 note:** Rev. 1 (map/path, tap-node-to-pan) shipped as slice 1 — cone-shaped deck nodes with `<Html>` card labels floating over a canvas (`apps/web/components/game/{map-node,beacon,dashboard-map-scene}.tsx`). User feedback: it still reads as a flat learning-card list with a 3D coat of paint, not a game. Rev. 2 replaces the genre: an explorable island the user's character walks around on foot, with decks/features as physical structures on the island. This section and Architecture/Screens/Visual identity below are rewritten; Data model, Motion rules, Performance & accessibility, Tech stack carry over from rev. 1 except where noted.

**Rev. 3 note:** Rev. 2's procedural-only art constraint is dropped. User wants the diorama look of a floating low-poly island — houses, trees, windmill, a river — with soft pastel colors, a split-screen DOM+3D dashboard layout, playful UI chrome (rounded buttons, avatar cards, drifting clouds), and a mouse-orbit camera alongside character movement. Rev. 3 switches character/prop art to curated CC0 (public-domain-equivalent, no-attribution) asset packs — Kenney.nl, Quaternius, Poly Pizza — instead of hand-built primitives, and adds orbit-camera + layout/visual-identity detail on top of rev. 2's mechanics (input, collision, interaction trigger, scene registry, fallback path), which are unchanged. Character controller, Visual identity, Tech stack additions, and Risks are revised below; everything else carries over from rev. 2.

**Rev. 3 addendum — cards go 3D too:** rev. 2 kept the study flashcard as a `<Html>`-text hybrid and left Deck Detail's card list as plain DOM (deliberately, as "data management, not a game moment"). User feedback: that's still a traditional card UI wearing a 3D coat, same complaint as rev. 1's map nodes. Addendum: the study card becomes a real textured mesh (not an Html billboard) and Deck Detail's browsing surface becomes a 3D "card shelf" scene inside the hut, while every actual text-entry form (add/edit card, bulk import) stays DOM — typing Chinese/pinyin/definitions into a 3D input is not a usability upgrade. See revised Screens table and new "Card rendering" section below.

## Intent

Current UI (Paper & Ink) reads as calm, content-first, minimal — correct for a productivity tool, but the user wants Colyglot to feel like _playing a game_ while learning, not filling out flashcard admin. Goal: turn the app into a persistent 3D world — one island the player's character walks around — built from real WebGL (`react-three-fiber`), while keeping the underlying learning mechanics (SRS grading, deck/card CRUD) and the existing Paper & Ink palette/typography as the literal source material for that world — a "papercraft" extension of the current aesthetic, not a replacement of it.

**Scope: whole-app redesign, one pass.** The island hub plus every screen's in-world treatment (study, completion, deck detail, ambient screens, auth) is designed and built together, not shipped as independent screen-by-screen slices. Every route gets a 3D presence (full interactive scene or ambient backdrop) — no route untouched, no separate "legacy" visual mode.

**Out of scope (explicitly ruled out during brainstorming):**

- No RPG companion/mascot/pet system — the player's own character is the only avatar, no collectible-creature layer.
- No hearts/lives gating mechanic — sessions aren't blocked by a lives system.
- No new color palette for UI chrome/HUD — DOM tokens (`--bg`, `--primary`, etc.) are unchanged; see Visual identity for how this interacts with baked asset-pack textures.
- No custom 3D modeling — art comes from curated free (CC0) asset packs, not commissioned/hand-authored models. No paid asset marketplace spend.
- No physics engine (Cannon/Rapier) — collision is simple circle/AABB math against a small list of static colliders (structures, island edge), not a rigid-body simulation.
- No character customization system beyond a small fixed set of avatar skins (if the chosen character pack ships variants) — not a full outfit/cosmetic economy.

## Architecture

**Persistent global Canvas.** One `<Canvas>` (react-three-fiber) mounts once in `app/layout.tsx` as a fixed full-viewport layer behind all DOM content. It is never unmounted between route navigations — this is the deliberate, highest-risk/highest-payoff choice from the three architectures considered (per-route Canvas and DOM-island alternatives were rejected for weaker world continuity). The existing `GameCanvasHost`/`SceneHost`/`useSceneStore`/`useScene` infrastructure from slice 1 (`apps/web/lib/three/*`, `apps/web/components/game/{game-canvas-host,scene-host}.tsx`) carries over unchanged — rev. 2 changes what gets registered as the active scene, not the hosting mechanism.

- **SceneRegistry** (Zustand store, already built): maps the active route to a scene descriptor. Scene ids: `island-hub` (dashboard), `onboarding-reveal` (first-run intro; the same island-hub world with a scripted reveal, reusing the hub scene), `card-shelf` (deck detail interior, rev. 3), `study-card`, `completion`. Route change swaps _content_ inside the persistent Canvas without tearing down the WebGL renderer/context.
- Ordinary DOM screens (Tags, Me, Settings, Subscription, Deck Export, Not Found) register **no scene** — rev. 3 decision: the persistent Canvas simply sits empty/transparent behind them at zero render cost instead of holding a dimmed island duplicate. World continuity comes from the Canvas never unmounting, not from every screen showing the island.
- Each page component registers its 3D content declaratively via `useScene(node)`, so page components stay readable without importing Three.js internals directly.
- `frameloop="demand"` normally, switched to `"always"` only while `island-hub` or `onboarding-reveal` is the active scene (character movement/reveal needs a running render loop) and back to `"demand"` for static scenes (study/completion/empty) — an addition to slice 1, which was `"demand"` everywhere because nothing animated every frame yet.

**Fallback path (required, not optional).** A capability check (WebGL support, `prefers-reduced-motion`, a coarse low-end heuristic) swaps the entire Canvas for a static illustrated PNG/SVG backdrop per scene; the DOM layer on top is unchanged either way. `onContextLost` / `onContextRestored` (WebGL context loss, a real risk for a long-lived single context) trigger the same fallback rather than a blank canvas. When `prefers-reduced-motion` or low-end forces the fallback, the island hub degrades to the rev. 1-style static map (tap a node card to navigate) rather than being unusable — walking is an enhancement, not the only way to reach a deck.

## Character controller

- **Rig (rev. 3 — asset-based):** a CC0 GLTF character with baked idle/walk animations (Quaternius or a Poly Pizza equivalent — pick one pack with both clips so there's no animation-retargeting work), loaded via drei's `useGLTF` + played via `useAnimations`. Walk clip plays while `movementInput` magnitude > 0, crossfades to idle at rest (`actions.walk.fadeOut()` / `actions.idle.fadeIn()`, ~150ms crossfade, avoids a hard pose pop). If the chosen pack ships palette-swap variants, expose a small fixed set (3-4) as the avatar-selection choices for onboarding (see Screens/Out-of-scope) — otherwise ship the single default skin and drop avatar selection without blocking the rest of rev. 3.
- **Movement:** WASD on desktop (`keydown`/`keyup` listeners into a `useKeyboardInput()` hook returning a normalized direction vector) and an on-screen virtual joystick (drei-free custom `<VirtualJoystick>` DOM overlay, pointer events, same normalized-vector output) on touch — both feed the same `movementInput: { x: number; z: number }` so the character/camera code is input-source-agnostic. Movement is world-relative (not camera-relative) so orbiting the camera never changes what "W" means mid-walk.
- **Camera (rev. 3 — orbit + follow hybrid):** drei's `<OrbitControls makeDefault>` with `target` re-synced to the character's live position every frame (`controls.target.copy(characterPos)`), `enablePan={false}`, `enableDamping` on. Default distance/polar angle is a fixed isometric-leaning framing (roughly 35-45° above the horizon, matching the diorama reference) — `minPolarAngle`/`maxPolarAngle` clamp so the player can orbit left/right and tilt somewhat but can't flip to a top-down or below-ground view. The camera does **not** auto-recenter behind the character on movement (classic free third-person orbit, not a rigid chase cam) — simpler to implement correctly and avoids the camera fighting a player who's mid-drag; `minDistance`/`maxDistance` keep zoom within a sane range. Touch: one-finger drag on the canvas orbits (doesn't conflict with the joystick, which owns its own bottom-left hit-region).
- **Collision:** flat list of static colliders per island (`{ position: Vector2; radius: number }` for structures, plus one large circle for the island edge). Each frame: compute the character's next position from input, then for each collider push the position back out to `radius + characterRadius` if it overlaps — simple circle-vs-circle resolution, no physics engine, matches the existing "no Cannon/Rapier" constraint.
- **Interaction trigger:** each structure collider also carries a larger, non-blocking "interact radius." Entering it shows a `<Html>` prompt ("Press E to study" / tap prompt on touch) above the structure; pressing E / tapping it triggers the same navigation that used to be the map node's `<Link>` (route push to `/decks/[id]` etc.) — the DOM-driven learning flow underneath is unchanged, only how the player reaches it changes.

## Card rendering (rev. 3 addendum)

Cards carry live, per-user text content (hanzi, pinyin, definitions) — no asset pack has that baked in, so cards can't be a downloaded GLTF the way huts/trees are. Instead: a thin `RoundedBoxGeometry` (drei) "papercraft tile" mesh, with front/back faces textured by a `THREE.CanvasTexture` drawn from an offscreen 2D `<canvas>` (draw the hanzi/pinyin/meaning with the existing `font-hanzi`/`font-sans` stack, same as today's DOM card, just rasterized to a texture instead of rendered as DOM). This gets a real solid 3D object — thickness, correct lighting/shadow, flips and tosses like a physical card — while keeping arbitrary/dynamic text, full font support, and no new asset dependency. Regenerate the texture only when the card's content or grade-state changes (not every frame).

- **Study card:** the `FlipCard3D` tile sits on a small pedestal/desk prop (desk view, per Screens table); flips via mesh rotation (front/back canvas-textured faces) instead of an `<Html>` overlay. On grade, instead of only a particle burst, the card itself animates off the pedestal into a growing "studied" pile to the side (position/rotation lerp to a stacked offset) — visible session progress as a physical pile, not just a counter.
- **Deck Detail → card shelf:** replaces rev. 2's "ambient backdrop, DOM list unchanged" verdict. Entering a hut's interact radius and confirming now transitions the camera into that hut's interior — a small room (floor + back wall + a shelf prop) — where each card in the deck renders as a small tile on the shelf in a grid, same canvas-texture technique showing a preview (front hanzi character), tinted/glowing by due/mastered state via theme tokens (not baked color, since this is a procedural tile, not an asset). Clicking/tapping a tile opens the existing add/edit dialog unchanged — text entry stays a real form, only the browsing surface is 3D. A distinct glowing tile triggers "add card." The pinned **Study now**/"Play" affordance becomes an object in this room (a lectern/altar) rather than a floating button, matching rev. 3's Visual identity note on playful CTA styling.

## Migration from slice 1

Carries over unchanged: `apps/web/lib/three/{capability,use-render-capability,scene-store,use-scene,tokens}.ts`, `apps/web/components/game/{game-canvas-host,scene-host,fallback-backdrop}.tsx`, the `app/layout.tsx` mount.

Replaced by the island-hub scene + character controller (this rev.): `apps/web/components/game/{map-node,beacon,dashboard-map-scene,dashboard-map-bridge}.tsx` — the cone/`<Html>`-card node approach is fully superseded, not extended. `Beacon`'s visual (lit landmark) survives as a concept but gets rebuilt as a static island prop, not a standalone scene participant.

## Visual identity

- **Palette (rev. 3):** asset-pack textures are baked, not swappable 1:1 like procedural `MeshStandardMaterial` colors were — pick packs whose native palette is already soft mint/turquoise/earth-tone (Kenney's nature/city kits and Quaternius's are both low-saturation pastel by default, so this is a curation step, not a rebuild). Theme tokens still drive everything that's dynamic or DOM-adjacent: `--accent` → beacon flame/streak fire emissive, `--success`/`--danger`/`--warning` → grade particle colors, hut door-open/closed and due-badge colors, and all HUD/DOM chrome. Dark mode dims/relights the scene (ambient + directional light intensity/color driven by `[data-theme="dark"]`, via `useThemeTokens()`) rather than repainting every baked texture.
- **Geometry:** curated CC0 low-poly asset packs (Kenney.nl, Quaternius, Poly Pizza — GLTF/GLB, no attribution required) for the character, huts/houses, trees, and windmill. Island terrain stays a simple procedural landmass (a subtly-domed disc/extruded shape, flat-shaded, token-tinted) since it must resize/reshape with the deck count — not worth sourcing or wrestling a fixed-size terrain asset for. The river is a procedural plane with a slow scrolling UV/color offset (cheap animated water look, no shader library). Drifting background clouds are procedural low-poly clusters (grouped rounded boxes/spheres), `useFrame`-translated with wraparound — simplest way to get the "fluffy stylized clouds" look without another asset dependency. All downloaded assets are compressed (`gltf-transform`, Draco/Meshopt) before committing, per the bundle-weight risk below.
- **Typography in 3D:** hanzi/text labels and interaction prompts render via drei's `<Html>` (real DOM text billboarded over the 3D object), not 3D text geometry — preserves `font-hanzi`, screen-reader access, and avoids a font-to-3D-geometry pipeline.
- **Dashboard layout (rev. 3 — split-screen):** on wide viewports, the Dashboard's DOM content (heading, streak/XP summary, "Play" CTA, avatar-skin picker if shipped) is constrained to a left column (roughly the left 40-45% of the viewport, same max-width discipline as the rest of the DOM layer); the persistent full-viewport Canvas underneath is unchanged (per Architecture — one global Canvas, never re-parented into a panel), but the follow-camera's default framing is offset so the island/character composition reads as sitting in the uncovered right two-thirds of the screen. Below a layout breakpoint (phones), it collapses to the existing full-bleed pattern — DOM content overlays the top, island fills the viewport, matching every other screen's mobile treatment.
- **Playful UI chrome (rev. 3):** Dashboard/onboarding CTAs use a fully-rounded (`rounded-full`) button style with a dark-green fill variant (new `--cta-dark` token or `--primary-700`-equivalent — confirm exact token name against DESIGN.md's existing scale, don't invent a parallel one) for the primary "Play"/"Start" action; avatar-skin choices (if shipped) render as small rounded selection cards (existing `Cell`/card visual language, not a new component family) rather than a bare list.

## Data model

New table `deckProgress`: `deck_id, user_id, xp, level, updated_at` (ownership verified through `deck_id` → `decks.user_id`, same pattern as every other repository per AGENTS.md's hard constraint). Upserted inside the existing grading server action, at the same point it already writes `reviewLogs` — an added write, not a new user-facing flow. `level = floor(xp / 100) + 1` (placeholder curve, tunable). Completion-screen stars/medal are computed from session accuracy at render time, not persisted.

## Motion rules (extends DESIGN.md's Motion section)

- Character movement/camera-follow: continuous, driven by input each frame — no fixed duration, but follow-camera lerp factor is tuned so it settles within ~400ms of a direction change (feels responsive, not laggy or snappy-rigid).
- Camera cuts (island ↔ study desk ↔ ambient pull-back): ≤600ms ease-out (longer than the existing 300ms UI cap — camera travel reads differently from a sheet/dialog).
- Particle bursts: ≤800ms then settle.
- Card flip: keeps the existing ~350ms budget, now driven by mesh rotation instead of CSS `rotate-y-180`.
- `prefers-reduced-motion` collapses all of the above globally, and additionally disables free character movement — the island-hub scene falls back to the rev. 1 static tap-node map (see Architecture's fallback path) rather than forcing continuous motion on someone who opted out of it.

## Performance & accessibility

- `frameloop="demand"` for static scenes (study/completion/ambient); `"always"` only while island-hub is active and focused, since character movement needs a running render loop — switched back to `"demand"` the moment that scene isn't the foreground (tab hidden, route navigated away).
- Capability + reduced-motion + low-end heuristic gate: real WebGL scene vs static illustrated fallback, decided once per session and re-checked on `onContextLost`.
- Cleanup: scene swap disposes unused geometries/materials on route change (per web3d-integration-patterns' memory-leak pitfall) — nothing accumulates across a session's navigation.
- Keyboard input for movement (`WASD`) must not fight normal page keyboard navigation — the listener only drives the character while the island-hub scene has DOM focus/is the active route, and never calls `preventDefault()` on keys that aren't W/A/S/D.
- Virtual joystick is a touch-only overlay (`pointer` events, hidden on non-touch viewports) — doesn't compete with a mouse cursor on desktop.
- Every structure's interact prompt is reachable without free movement too: the fallback static map (reduced-motion or low-end) exposes the same decks as tappable cards, so navigation to any deck never strictly requires successfully walking a character.

## Testing

- Unit tests: SceneRegistry swap logic, XP/level math, and the collision-resolution function (circle-vs-circle push-out, pure — same style as `packages/srs`) as pure functions.
- E2E (Playwright): existing specs keep testing DOM behavior/copy/state; gated behind a capability flag so CI doesn't require real WebGL. New: an E2E path that forces the static fallback and asserts deck navigation still works without any character movement.
- Visual/render correctness: manual QA only, not automated — no visual-regression tooling in scope. Character walk-cycle/collision feel is judged by hand on a real device, not asserted in a test.

## Tech stack additions

`three`, `@react-three/fiber`, `@react-three/drei` (now load-bearing for `useGLTF`/`useAnimations`/`OrbitControls`, not just `<Html>`), `zustand`. Dev-time only: `gltf-transform` CLI (compress/optimize downloaded GLTFs before committing — not a runtime dependency). No GSAP, no Framer Motion, no physics engine (Cannon) — deliberately excluded: DOM motion stays the existing CSS keyframe system, camera/intro sequences use a `useFrame` lerp instead of a timeline library, and there are no drag/physics interactions in this design. Per AGENTS.md, these are genuinely new shared needs (3D rendering, cross-page 3D state) — not speculative.

**Asset sourcing:** CC0-licensed packs only (no attribution required, no per-asset license tracking burden) from Kenney.nl, Quaternius, and/or Poly Pizza. Downloaded models live under `apps/web/public/models/`, alongside a single `LICENSES.md` recording pack name + source URL + license (even though CC0 needs no attribution, tracking provenance matters if a pack is ever swapped later).

## Risks (accepted, not deferred)

- **Persistent-Canvas-across-navigation is the unproven part of this design.** Next.js App Router navigation + a WebGL context that must survive it is the single biggest technical risk in this spec — mitigated by the fallback path and `onContextLost` handling, but not eliminated. This was a deliberate choice (highest immersion) over the safer per-route-Canvas alternative.
- **Bundle weight / low-end mobile performance** for a mobile-first app taking on real WebGL, now with a continuously-running (`frameloop="always"`) render loop while the hub is active instead of `"demand"` everywhere, plus (rev. 3) real downloaded GLTF assets instead of zero-weight primitives — mitigated by the capability-gated fallback and mandatory Draco/Meshopt compression of every asset before commit, but battery/thermal impact and total scene download size on real mobile devices are both untested and are the main new risks rev. 3 adds on top of rev. 2.
- **Asset sourcing/curation is the new bigger, more visible build vs. rev. 2's procedural rig.** Finding a character pack with both walk+idle clips, a coherent pastel palette across character/hut/tree/windmill packs (mixing packs from different authors risks a visually inconsistent island), and keeping combined GLTF size small enough for a mobile-first app are all hands-on curation problems this spec sets direction for but doesn't pre-select exact assets for. Collision fairness (not clipping into huts, not sticking on the island edge) and an orbit camera that doesn't fight the player are still iteration-heavy tuning work regardless of art source.
- **Whole-app-in-one-pass scope is higher-risk than rev. 1's incremental rollout.** Nothing ships to real users until island hub + study + completion + ambient + auth are all done, versus rev. 1's screen-by-screen releases. Accepted per explicit user direction, but means no early production feedback until the full pass lands.
- **Discoverability:** with no forced path (unlike rev. 1's fixed node layout), a player could spawn on the island and not know where the huts are or what to do. Out of scope for this spec to solve in full, but the onboarding "world reveal" and a visible beacon landmark are the intended first mitigations — may need a compass/arrow HUD element if playtesting shows people get lost.
